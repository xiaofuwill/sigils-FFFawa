# M2 Session Server Contract

## Compatibility source

The relay mirrors the SIGILS v4.3 session flow and message envelope. The four-character uppercase session code (`A`–`Z`) is generated by the CC:Tweaked program (`Utils.randomString(4)`) and sent in `SessionCreate`; the relay must not generate or transform it. The relay returns a UUID `ccReconnectToken` in a successful `ConfirmationResponse`.

The game-side endpoint is configurable through `sigils-config.json`:

```json
{
  "server": "wss://your-host.example",
  "logLevel": 1,
  "minCycleInterval": 0.025
}
```

Use `wss://` for a public deployment behind TLS. The relay does not modify the SIGILS wire protocol.

## Session lifecycle

1. CC opens the WebSocket and sends `SessionCreate` with its four-character uppercase (`A`–`Z`) `sessionId` and `reqId`.
2. Relay registers the session and replies with `ConfirmationResponse` (`respondingTo: SessionCreate`, `ok: true`, `ccReconnectToken`).
3. Browser sends `SessionJoin` with the same `sessionId`; relay returns a successful `ConfirmationResponse`.
4. Browser requests `FactoryGet`; relay forwards the exact JSON message to CC.
5. CC replies with `FactoryGet` confirmation and full `factory`; subsequent CRUD and `BatchRequest` traffic is relayed without interpreting Factory state.
6. CC reconnects with `SessionRejoin`, the original `sessionId`, and the original `ccReconnectToken`.

## Relay behavior

- One active editor per session.
- The CC peer is the authority for Factory data and persistence. The relay stores no Factory snapshot and has no database.
- Editor messages received while CC is temporarily disconnected are queued for up to `OUTBOX_TIMEOUT_MS` (default 10 seconds).
- Queued messages are flushed FIFO after the successful `SessionRejoin` response. The response must be sent first because the CC client waits synchronously for it during reconnect.
- Session idle timeout defaults to 10 minutes, matching the upstream server behavior.
- A stale socket closing after a reconnect must not detach the replacement socket.
- WebSocket payload limit defaults to 100 MiB, matching the `ws` library default used by the upstream server; configure `MAX_PAYLOAD_BYTES` to impose a tighter deployment-specific cap.
- `ALLOWED_ORIGINS` is optional. When set, browser origins must match one of its comma-separated values. CC clients that omit an Origin header remain accepted.

## Deliberate non-goals

- No server-side Factory mutation, JSON overwrite, or persistence.
- No change to request names, `reqId`, `ConfirmationResponse`, `CcUpdatedFactory`, or jsondiffpatch delta payloads.
- No authentication redesign in M2. A four-character code is a pairing code, not a high-entropy credential; deploy behind TLS and avoid exposing operational logs or session metadata.

## Endpoints

- `GET /healthz`: process health response.
- `GET /`: plain-text service identity.
- WebSocket upgrade on `/` (same origin/port).
