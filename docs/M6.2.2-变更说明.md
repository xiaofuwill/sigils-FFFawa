# M6.2.2 — 变更说明（CC 批量执行与持久化语义）

**日期：** 2026-11-12
**版本：** M6.2.2
**性质：** 稳定性补丁，不扩展功能
**协议：** SIGILS v4.3（消息字段未变）

---

## 一、审计修正

M6.2.1 的审计对象是 `SIGILS-upstream-master`（较新的控制器实现）。实际部署基线 `sigils-v4.3-source` 已经具备：

- `staged = cloneValue(factory)`；
- 子请求操作 staged；
- 先 `Factory.saveFactory(staged)`，成功后才 `commitFactory` 与发送成功响应。

因此，对**实际部署源码**的 BatchRequest 结论应修正为：**顺序执行 + 单次保存 + 成功后提交（staged commit）**，执行失败会丢弃 staged，内存 Factory 不变；但仍**不是**崩溃安全事务，也不保证文件系统级原子替换。

本次按 M6.2.2 任务书补上仍然缺失的部分：确定性数组校验、完整子请求预校验、未知类型拒绝、保存结果显式检查、保存失败后的写入门禁。

## 二、CC Lua 变更

| 文件 | 变更 |
|---|---|
| `sigils/batchValidation.lua`（新增） | 纯 Lua 预校验：数组连续非空、11 种 mutation 类型白名单、必需字段 / 可选字段类型、槽位结构 |
| `sigils/controller.lua` | `BatchValidation` 预校验后用 `ipairs` 顺序执行；未知类型/缺字段在 mutation 前拒绝；`saveFactory` 必须显式返回 `true`；新增 `persistenceFailed` latch；失败响应带 `error/message`；外设事件保存同样检查返回值 |
| `sigils/factory.lua` | `saveFactory` 成功时显式 `return true` |
| `sigils-v4.3-packager.lua` | 兼容 Lua 5.5（循环变量改为局部变量），便于在 PC 上重新打包与测试 |

### 保存失败后的行为

1. 不提交 staged，Factory 内存保持原状；
2. 不发送成功确认，返回 `ok=false` + `message`；
3. `persistenceFailed = true`，此后所有 mutation 与 FactoryGet 直接返回失败，直到重启 SIGILS 并通过 `recoverFactory` 重建权威状态；
4. 不自动重试。

### 批量执行失败语义

| 阶段 | 结果 |
|---|---|
| 预校验失败 | `rejected_before_mutation`：未执行任何子请求，无保存，Factory 不变 |
| 子请求执行失败 | `execution_failed_after_partial_mutation`：staged 被丢弃，内存 Factory 不变；不是数据库式回滚，但不会提交半成品 |
| 保存失败 | `save_failed_after_mutation`：不提交，进入 `persistenceFailed` |
| 保存成功 | `saved`：提交 staged 并发送成功响应 |

## 三、Factory writer 审计结论

| 位置 | 分类 | 说明 |
|---|---|---|
| `sigils.lua` 启动 | FACTORY_WRITER | `updateWithPeriphChanges` + `saveFactory`，在所有协程启动前执行 |
| `controller.lua` | FACTORY_WRITER | 唯一运行时 writer，单 `os.pullEvent` 循环串行处理 |
| `factory.lua` | FACTORY_WRITER（被调用） | 只修改调用方传入的 staged 表；控制器/启动流程是唯一调用者 |
| `pipe.lua` | READ_ONLY + TRANSIENT_ONLY | 读取 `factory.pipes/groups/missing`，写入仅限局部表与 `ItemDetailAndLimitCache` / `PeripheralCache` |
| `pipeBatcher.lua` / `PipeGraph.lua` / `PipeSaturation.lua` | READ_ONLY | 只计算批次与图 |
| `packageTransport.lua` | READ_ONLY + TRANSIENT_ONLY | 运行时地址/类型缓存在模块表，不写 Factory |
| `PeripheralCache` / `ItemDetailAndLimitCache` | TRANSIENT_ONLY | 运行时缓存，不参与 factory.json 序列化 |
| `backup-factory.lua` | 文件维护 | 只做 `factory.json` → `factory.json.bak` 备份 |
| `machine.lua` | 构造器 | 生成新机器/分组表，不写现有 Factory |

**结论：** 运行时唯一持久化 Factory writer 是 Controller；Pipe 协程会 yield，但只读 Factory。FIFO stale barrier 的前提仍然成立。Pipe 可能在 yield 后持有已被替换的旧表引用，属于“读旧配置”风险，不会写坏 Factory。

## 六、兼容性

- 消息类型、字段、`factory.json` 结构、过滤器语法、Create 运输语义均未改变。
- 失败响应新增 `error/message` 字段（v4.3 `ConfirmationResponse` 已定义），前端已有展示逻辑。
- 旧版编辑器向 BatchRequest 塞未知子请求时，将收到 `ok=false`（此前被静默忽略）；这是有意的 fail-closed 变更。
