# M6.2.2.2 — 变更说明（BatchRequest 深层字段校验）

**日期：** 2026-11-12
**版本：** M6.2.2.2（指导包内部编号 M6.2.2.1）
**性质：** 校验加固补丁，不扩展功能
**协议：** SIGILS v4.3（消息类型与字段未变）

---

## 一、问题

M6.2.2 已让 `batchValidation.lua` 校验数组连续性、child 类型白名单和部分必填字段，但仍有三类缺口：

1. `PipeEdit` / `MachineEdit` / `GroupEdit` 的 `edits` 只检查是否为 table，任意键都会被 `Factory.*Edit` 写进 Factory。
2. `PipeAdd` / `MachineAdd` / `GroupAdd` 的嵌套对象只检查少量必填字段，未知字段会原样写入。
3. `PeriphAdd.options` 会被 `Factory.periphAdd` 原样覆盖到新建 Machine 上，可借此改写 `id`、`groups` 等身份/关系字段。

本轮把 CC Lua 变成最终权威校验点，并让 TypeScript 模拟层使用同一契约。

## 二、字段契约

| 请求 | 允许字段 | 必填 / 约束 | 明确拒绝 |
|---|---|---|---|
| `PipeAdd` | 顶层 `type/reqId/pipe`；`pipe`: `id/from/to/mode/nickname/filter` | `id/from/to` 非空字符串；`mode` 仅 `natural/spread`；`nickname/filter` 字符串（可为空） | 任何额外键 |
| `PipeEdit` | 顶层 `type/reqId/pipeId/edits`；`edits`: `mode/nickname/filter` | `pipeId` 非空；`mode` 枚举；`nickname/filter` 字符串 | `id`、`from`、`to`、未知键 |
| `PipeDel` | `type/reqId/pipeId` | `pipeId` 非空 | 额外键 |
| `MachineAdd` | 顶层 `type/reqId/machine`；`machine`: `id/groups/nickname/x/y` | `id` 非空；`groups` 连续字符串数组；坐标有限数 | `fluid`、未知键 |
| `MachineEdit` | 顶层 `type/reqId/machineId/edits`；`edits`: `nickname/x/y` | 坐标有限数 | `id`、`groups`、`periphId`、未知键 |
| `MachineDel` | `type/reqId/machineId` | `machineId` 非空 | 额外键 |
| `GroupAdd` | 顶层 `type/reqId/group/machineId`；`group`: `id/slots/nickname/x/y/fluid` | `id` 非空；`slots` 连续数组；每个 slot 仅 `periphId/slot`；`periphId` 非空；`slot` 正整数；`fluid` boolean；坐标有限数；`machineId` 若非空必须是非空字符串 | 未知键、sparse slots、slot 内额外字段 |
| `GroupEdit` | 顶层 `type/reqId/groupId/edits`；`edits`: `nickname/x/y/fluid/slots` | `slots` 规则同上；坐标有限数 | `id`、`machineId`、未知键 |
| `GroupDel` | `type/reqId/groupId` | `groupId` 非空 | 额外键 |
| `PeriphAdd` | 顶层 `type/reqId/periphId/options`；`options`: `nickname/x/y` | `periphId` 非空；`options` 可省略；坐标有限数 | `id`、`groups`、`periphId`、未知键 |
| `PeriphDel` | `type/reqId/periphId` | `periphId` 非空 | 额外键 |

通用规则：

- 每个 child 必须是 table，`type` 为 11 种 mutation 之一；`reqId` 若存在必须是非空字符串。
- 外层 `requests` 必须是非空、连续、从 1 开始的数组；拒绝稀疏数组、字符串 key、小数 key。
- 数值必须是有限数；NaN、`math.huge`、`-math.huge` 一律拒绝。
- 未知字段默认拒绝，错误消息包含 `request N (Type): ...` 和具体字段路径。

## 三、设计决定

- **`MachineEdit` 不接受 `groups`。** `groups` 是 Machine 与 Group 的关系字段，通用 Edit 直接覆盖会破坏双向引用；现有 Web 端也不通过 `MachineEdit` 修改 groups（分组归属由 `GroupAdd.machineId` / `GroupDel` 维护）。因此列为禁止字段，而不是放行后补一致性逻辑。
- **`GroupEdit` 接受 `fluid`。** 它是 Group 自身属性（boolean），不是关系字段。
- **`PeriphAdd.options` 只允许 `nickname/x/y`。** 与现有 `buildPeripheralAdd` 实际发送的 `{x, y}` 一致；身份字段由 `periphId` 和外设模板决定。
- **强制要求 `pipe.mode` 为枚举。** 现有 Web 端不发送 `mode`；一旦发送，只接受 `natural` / `spread`。

## 四、执行顺序与失败语义

```text
Editor -> CC: BatchRequest
CC: countArray(requests) + 每个 child 的字段白名单/类型/边界校验
    ├─ 任一失败 -> ok=false + 诊断 message；Factory 不变；不 save；不发送成功
    └─ 全部通过
CC: staged = clone(factory)
CC: 按 ipairs 顺序执行 children（只改 staged）
CC: saveFactory(staged) 必须显式返回 true
CC: commitFactory(factory, staged)
CC -> Editor: ok=true + diff
```

- 本轮没有改变任何执行顺序或保存时序，只把校验从“浅层”扩展到“深层”。
- 仍然**不是**数据库事务；文件系统故障一致性未在本轮证明。

## 六、兼容性

- 消息类型、字段名、成功响应、`factory.json` 结构、过滤器语法、Create 物流均未修改。
- 合法请求行为不变；非法请求从“可能写入”变为“整批拒绝”。
- 旧客户端若通过 `edits` 发送 `id/groups/from/to` 或向 `options` 注入身份字段，将收到 `ok=false`。这是有意的 fail-closed 变更。
