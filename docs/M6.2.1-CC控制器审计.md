# M6.2.1｜CC 控制器审计（BatchRequest 与同步屏障）

**日期：** 2026-11-12
**审计对象：** `SIGILS-upstream-master/SIGILS-master/computercraft/sigils/`
**结论摘要：**

1. **同步屏障成立（有源码证据）**：CC 单协程 FIFO 事件队列保证“晚于 mutation 发出的 FactoryGet”在 mutation 执行并保存之后才取快照。
2. **BatchRequest 不是事务**：子请求顺序修改同一个 Factory 对象，整批结束后只保存一次；中途异常没有回滚，且会中断控制器协程。归类为 **C（单次持久化但非事务）**。
3. Fake CC 的 staged clone + 单次保存比真实 CC 更“原子”，**不能**作为真实原子性的证据。

---

## 一、调用链与证据

### 1. WebSocket 消息 → OS 事件

`computercraft/sigils/websocket.lua`

| 行 | 内容 |
|---|---|
| 118–138 | `queueEventFromMessage(message)`：对已知类型执行 `os.queueEvent('ccpipes-' .. messageType, message)`（第 128 行） |
| 174–198 | CONNECTED 状态用 `ws.receive()` 收消息，解析后调用 `queueEventFromMessage` |

结论：编辑器请求不会在 WebSocket 协程里直接执行，而是按到达顺序进入 CC 的 OS 事件队列。

### 2. OS 事件 → controller 单协程

`computercraft/sigils.lua`：`parallel.waitForAll(WebSocket.doWebSocket, Controller.listenForCcpipesEvents, Pipe.processAllPipesForever, waitForQuitKey, sleepLoop)`（80–86 行）。

`computercraft/sigils/controller.lua`

| 行 | 内容 |
|---|---|
| 123–168 | `while true do local event, message = os.pullEvent()` 单循环 |
| 126–139 | 事件到 handler 的映射（`ccpipes-FactoryGet`、`ccpipes-<Mutation>`） |
| 141–153 | `BatchRequest`：遍历 `message.requests`，逐条调用 handler，最后一次性发送确认响应 |
| 154–158 | 单请求：调用对应 handler 并发送响应 |
| 165–167 | 除 `FactoryGet` 外，事件处理结束后调用 `Factory.saveFactory(factory)` |
| 5–14 | `handleFactoryGet`：直接返回当前 `factory` 的完整快照，不保存 |

handler 内部没有 `os.pullEvent` / `os.sleep`，单个事件处理期间不会让出协程，因此事件之间不存在交错执行。

### 3. 屏障推论

在“单编辑器 + relay 保序转发 + controller 单协程 FIFO”的前提下：

```text
T0 Browser -> CC: Mutation A      （先到达，先入队）
T1 Browser: A 超时，进入 stale
T2 Browser -> CC: FactoryGet      （后入队）
T3 CC: 处理 A -> 修改内存 -> saveFactory
T4 CC: 处理 FactoryGet -> 返回 A 保存后的快照
T5 Browser: 收到快照
```

T3 必然早于 T4，因此快照覆盖 A 的结果，不存在“A 在快照之后提交”的路径。

前提证据：

- 单编辑器：relay `SessionManager.join` 在已有打开 editor 时拒绝（`apps/server/src/session-manager.ts` 47–53）。
- 保序转发：relay 收到编辑器消息后立即转发给 CC（`apps/server/src/index.ts` 170–183），CC 断开时进入 FIFO outbox 并在 rejoin 后按顺序 flush（`session-manager.ts` 67–75）。
- 失败路径：outbox 超时会整批丢弃（`session-manager.ts` 77–86），不会出现“mutation 被保留而 FactoryGet 被丢弃”的乱序。

### 4. 屏障的边界与限制

- 若控制器协程因异常退出（见第二节），不会再有快照响应，客户端保持 stale。
- 屏障只覆盖“同一 Session、同一 controller 进程”内的写入；跨会话/重启等同于新的权威状态，通过完整快照重新建立。
- 浏览器端 `epoch` / `mutationSeq` 只是拒绝错配与保证“快照请求晚于全部写入”的本地断言，**不是**屏障本身。

## 二、BatchRequest 提交语义（结论 C）

### 1. 关键代码

`computercraft/sigils/controller.lua`

```lua
if event == 'ccpipes-BatchRequest' then
  local diffs = {}
  for i, request in pairs(message.requests) do
    local handlerName = 'ccpipes-' .. request.type
    if handlers[handlerName] then
      local diff = Utils.freezeTable(handlers[handlerName](request, factory, sendMessage))
      if (diff ~= nil) then table.insert(diffs, diff) end
    end
  end
  diffs = Utils.concatArrays(unpack(diffs))
  sendMessage(textutils.serializeJSON(createConfirmationResponse(message, true, diffs)))
elseif ...
end

if (...) and event ~= 'ccpipes-FactoryGet' then
  Factory.saveFactory(factory)
end
```

`computercraft/sigils/factory.lua`

```lua
local function saveFactory(factory)
  local json = textutils.serializeJSON(factory)
  local f = fs.open(Utils.absolutePathTo('factory.json'), 'w')
  f.write(json)
  f.close()
end
```

### 2. 逐项回答

| 问题 | 结论 |
|---|---|
| 子请求是否顺序执行 | 是，按 `message.requests` 数组顺序 |
| 某子请求失败后是否继续 | 不会继续：handler 抛错会向上传播，循环中断 |
| 是否修改当前 Factory | 是，handler 直接读写同一个 `factory` 表（如 `factory.lua` 83–101 `machineEdit`、205–223 `groupEdit`） |
| 是否使用临时副本 | 否 |
| 成功是否只有一次持久化 | 是，整批结束后一次 `saveFactory` |
| 中途失败是否回滚内存 | **否**，没有 pcall、没有 staged clone、没有回滚 |
| 持久化失败如何处理 | `saveFactory` 无 pcall、无原子替换；`fs.open` 返回 nil 时会抛错，内存与磁盘可能不一致 |
| 响应能否准确表达结果 | 成功路径统一 `ok=true`；未知子类型被静默跳过仍返回 `ok=true` |
| 响应与保存顺序 | 先发送响应，再 `saveFactory`（同一协程内），所以“收到 ok”不等于“已落盘” |

### 3. 结论

**分类 C：单次持久化但非事务。**

- 正常路径：全部子请求修改内存 → 响应 ok → 一次保存。
- 异常路径：已执行的子请求留在内存；未保存；控制器协程可能终止。
- 不能对外宣称“原子合并 / 原子批量”；客户端只能依赖**预校验**降低失败概率，并在失败/断线时进入 stale 通过快照恢复。

### 4. Fake CC 的差异（必须标注）

`tests/support/fake-cc.ts` 使用 staged clone、保存成功后才提交，并支持 `failSaves` 回滚。这比真实 CC 更安全，**只用于协议语义测试，不能证明真实 CC 的原子性**。

## 三、对实现的直接影响

1. `BatchRequest` 仍只按“一个 mutation”受单飞门禁约束；但报告与 UI 不宣称原子回滚。
2. 容器合并、槽位拆分、多管道删除都依赖客户端预校验；失败时通过 stale + 完整快照恢复，而不是尝试“逆向补偿”。
3. `saveFactory` 失败可能导致控制器退出；此时不会有任何快照响应，客户端保持只读 stale，需人工重启控制器后重新连接。
4. 同步恢复以 CC FIFO 屏障为依据；前端 epoch / seq 仅用于拒绝错配和覆盖校验。

## 五、M6.2.2 补充说明（审计对象修正）

本文件第二节的结论基于 `SIGILS-upstream-master`（较新的控制器实现）：它先发送成功响应、再 `saveFactory`，且未知批量类型被静默跳过。
