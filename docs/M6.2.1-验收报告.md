## 3. 请求响应严格匹配

- **reqId**：必须命中当前 pending；未知 reqId 只记录并忽略。
- **respondingTo**：必须与 pending 中记录的原始请求类型完全一致；BatchRequest 必须精确匹配 `BatchRequest`，子请求响应不能冒充。
- **payload schema**：FactoryGet 要求 `factory` 为对象，并继续做 `validateFactoryShape` + `validateFactoryReferences`；工厂写入/BatchRequest 要求 `diff` 为数组；SessionJoin / SessionClose 不要求 diff。
- **Session**：pending 记录发出时的 Session Code，响应必须与当前一致。
- **connection epoch**：每条新连接递增，旧 epoch 响应拒绝。
- **顺序**：以上校验 + 完整快照校验全部通过后，才清 timer、删 pending、`guard.finish`、应用 Factory/diff、改变 stale。
- **错配响应测试**：R01–R10 全部通过（`tests/response-guard.test.ts`）。
- **迟到 / 重复响应测试**：未知 reqId 不产生状态变化；超时后迟到响应被忽略；重复响应只处理一次（R03/R06/S07 语义）。

## 4. stale 恢复屏障

- **屏障机制**：CC 单协程 FIFO 事件队列（`websocket.lua` `os.queueEvent` → `controller.lua` `os.pullEvent`）；mutation 在其事件内完成并 `saveFactory` 后才处理下一个事件。
- **CC 端证据**：`computercraft/sigils/websocket.lua` 118–138、`controller.lua` 5–14 / 123–168、`factory.lua` 16–21，详见 `M6.2.1-CC控制器审计.md`。
- **revision / sequence 定义**：现有协议没有 revision；客户端维护本地 `mutationSeq`，FactoryGet pending 记录发出时的序号。快照仅在 `snapshotSeq === currentSeq` 时可用于解除 stale。
- **超时 mutation 是否可能晚于快照提交**：在单编辑器、relay 保序转发、controller 单协程前提下为否；mutation 入队早于 FactoryGet，必然先执行并保存。
- **无屏障时是否保持只读**：是。覆盖校验失败 / 快照校验失败 / 快照请求失败都保持 stale，仅提示重新同步。

## 5. FactoryGet 单飞

- **同 Session 并发策略**：`FactorySyncGuard.begin` 检测到已有 FactoryGet 时抛错；UI 按钮在同步期间禁用并显示「正在同步…」。
- **重复请求行为**：明确拒绝（提示“已有 FactoryGet 同步请求正在进行”），不并发发起第二个快照。
- **Session 切换行为**：`connect` 主动清空 pending、标记旧请求失效并递增 generation；旧响应因 Session / epoch 不匹配被拒绝。
- **旧响应隔离测试**：R07 / R08；F01–F03（`tests/sync-guard.test.ts`）。

## 6. BatchRequest 真实源码审计

- **Lua 文件**：`computercraft/sigils/controller.lua`、`factory.lua`、`websocket.lua`
- **函数 / 行号**：`listenForCcpipesEvents` 107–169；批量分支 141–153；单请求 154–158；保存 165–167；`saveFactory` 16–21。
- **执行策略**：按数组顺序逐条调用 handler，直接修改同一个 `factory` 表。
- **失败回滚策略**：无 pcall、无 staged clone、无回滚；handler 抛错会中断循环并跳过保存。
- **saveFactory 时机**：整批 handler 与响应之后、下一个事件之前调用一次。
- **磁盘写入失败处理**：直接 `fs.open('w')` + `write` + `close`，无原子替换；`fs.open` 失败会抛错。
- **结论分类**：**C（单次持久化但非事务）**。
- **证据**：见 `M6.2.1-CC控制器审计.md` 第二节。
- **说明**：Fake CC 使用 staged clone，比真实 CC 更安全，不作为原子性证据。

## 7. 多管道删除

- 单条：直接 `PipeDel`。
- 多条：`buildPipeDeleteBatch` 生成一个 `BatchRequest`（多个 PipeDel 子请求），只占一个 mutation 名额。
- 测试：`tests/factory-actions.test.ts`（消息结构）、`tests/protocol-sim.test.ts`（Fake CC 一次批次删除两条管道）。
- UI：当前检视面板按单条管道操作；若 React Flow 传入多条选中边，也走单个批次。

## 10. 未解决问题与风险

1. **真实 CC / Minecraft / Create 未联调**：屏障结论来自 Lua 源码与模拟测试，需真机复核超时、断线、重连、外设插拔。
2. **无协议 revision**：覆盖判断依赖发送顺序与 CC FIFO 队列；若未来引入多编辑器、批量转发器或多线程控制器，该证明失效，需要协议级 revision。
3. **saveFactory 失败 / 控制器崩溃**：源码层分析为可能中断控制器且不保存；真机未验证，客户端会保持 stale，需要人工重启。
4. **浏览器故障注入未执行**：错配 / 迟到响应由纯函数测试覆盖，未在真实 WebSocket 会话中注入。
5. **多选管道删除**：UI 默认单条操作，批量路径已实现并测试，但浏览器多选行为未实测。
6. **mock CC 容量数据不完整**：不影响本轮同步安全结论。
