**日期：** 2026-11-12
**调查对象：** `SIGILS-upstream-master/SIGILS-master`（v4.3 原版编辑器 + CC Lua）
**目的：** 在改代码前确认旧版槽位拖动、容器合并、机器 / 外设编辑的真实语义。

> 本文件只记录源码事实与本项目采取的实现决策。“未确认”项必须等真实 CC 联调。

## 一、调查到的源码位置

| 关注点 | 上游文件 | 关键内容 |
|---|---|---|
| 槽位拖动起点 | `client/src/components/ItemSlot.tsx` | 每个槽位是 `draggable` 的 HTML 元素，`dragstart` 写入 `application/ccpipes-slotmove`，载荷 `{slot, machineId, oldGroupId}` |
| 槽位放下 | `client/src/GraphUpdateCallbacks.ts#onDrop` → `SplitHandlers.ts#splitSlotFromGroup` | 只接受命中的节点 `id === machineId`；源分组只剩 1 个槽位时不发请求；否则 `GroupAdd`（新分组仅含该槽位，沿用旧昵称）+ `GroupEdit`（从旧分组移除），装入一个 `BatchRequest` |
| 容器框定义 | `client/src/nodes/GroupNode.tsx`、`nodes/index.ts` | 画布上的“容器大框”就是 `slot-group` 节点，内部按 9 列网格渲染 `group.slots` |
| 容器拖动 / 合并 | `client/src/GraphUpdateCallbacks.ts#onNodeDrag/onNodeDragStop`、`CombineHandlers.ts#combineGroups` | 兼容目标：同为 `slot-group` 且 `parentId` 相同；结果：`GroupEdit`（目标 slots = 两者合并后排序）+ `GroupDel`（源），装入一个 `BatchRequest` |
| 合并兼容规则 | `CombineHandlers.ts#canCombine` | `Boolean(source.fluid) === Boolean(target.fluid)` |
| 合并排序 | `CombineHandlers.ts#combineGroups` | 先按 `slot` 升序，再按 `periphId` 字典序 |
| 机器框拖动 | `CombineHandlers.ts#combineMachines` | 上游还会合并同名分组、`MachineEdit` 目标 + `MachineDel` 源；**不属于 M6 要求，本版不实现** |
| 外设徽章拖动 | `components/PeripheralBadge.tsx`、`SplitHandlers.ts#splitPeripheralFromMachine` | 把某外设的槽位拆成新机器；多条请求、非原子；**本版不实现** |
| 机器 / 分组编辑面板 | `components/MachineOptions.tsx`、`GroupOptions.tsx` | 只有 Nickname 一个字段，没有 Peripheral ID 编辑 |
| Machine 数据结构 | `server/src/types/core-types.ts` | `Machine { id, groups, nickname?, x?, y? }`，没有外设 ID 字段 |
| Group 数据结构 | `server/src/types/core-types.ts` | `Group { id, slots, nickname?, x?, y?, fluid? }`，槽位身份是 `(periphId, slot)` |
| CC 侧编辑处理 | `computercraft/sigils/factory.lua#machineEdit/groupEdit` | 按键直接写入对象，不做引用或 ID 校验 |
| CC 侧批量语义 | `computercraft/sigils/controller.lua` | `BatchRequest` 逐条应用后只调用一次 `Factory.saveFactory` |
| 机器 / 分组 ID 生成 | `computercraft/sigils/machines/chest.lua`、`generic.lua`、`machine.lua` | `machine.id = periphId`；分组 ID 为 `<periphId>:gN` / `<periphId>:fluids` |

## 二、对照表

### 1. 槽位拖动

| 项 | 旧版行为 |
|---|---|
| 拖动对象 | 单个槽位方块 |
| 起点 | 任意展开容器内的槽位 |
| 有效目标 | 自己所属的机器框（`node.id === machineId`） |
| 跨机器 | 不允许，请求根本不生成 |
| 跨容器（同一机器） | 落点只看机器框，不区分落在哪个容器上 |
| 结果 | 该槽位从原容器移除，进入一个**新建容器**（沿用原容器昵称、fluid 属性），坐标为落点相对机器框的位置 |
| 边界 | 原容器只剩 1 个槽位时不做任何事（避免产生空容器） |
| 数据结构 | `GroupAdd` + `GroupEdit`，同一个 `BatchRequest` |
| 持久化 | CC 在整批请求后保存一次 |

### 2. 容器框拖动 / 合并

| 项 | 旧版行为 |
|---|---|
| 拖动对象 | 整个容器大框（`slot-group` 节点），不是槽位 |
| 有效目标 | 同一机器内（`parentId` 相同）的另一个容器框 |
| 类型兼容 | Item ↔ Item、Fluid ↔ Fluid；不能混 |
| 结果 | 源容器槽位并入目标容器，目标容器保留自己的 ID 与昵称，**源容器被删除** |
| 槽位身份 | 不变，仍是 `(periphId, slot)`，只改变所属容器 |
| 槽位顺序 | 合并后按 `slot` 升序、再按 `periphId` 字典序重排 |
| 关联管道 | 源容器被 `GroupDel` 删除时，CC 级联删除两端连接它的管道 |
| 数据结构 | `GroupEdit`（目标）+ `GroupDel`（源），同一个 `BatchRequest` |
| 撤销 | 上游没有撤销；`GroupDel` 后原 ID 与管道不可恢复 |

### 3. 机器框拖动

| 项 | 旧版行为 | 本版决策 |
|---|---|---|
| 拖动对象 | 机器框 | 同左，但只保存位置 |
| 合并 | 上游 `combineMachines` 会按昵称合并分组、删除源机器 | **不实现**（M6 未要求，且批量 `MachineDel` 的级联影响更大） |

### 4. Machine 的“机器”字段 / Peripheral ID

| 项 | 旧版行为 |
|---|---|
| 机器框标题 | `nickname || id`，`id` 等于外设 ID |
| 可编辑字段 | 只有 nickname |
| 外设 ID 编辑 | **不存在** |
| 数据层 | Machine 没有独立的外设字段；外设关联通过每个 `Slot.periphId` 表达 |
| 协议层 | `MachineEdit` 可写任意键，但不会重命名 map key、分组 ID、槽位 `periphId` 或管道端点 |
| 结论 | 仅靠现有协议无法安全改写外设 ID，见 `docs/M6-I4-外设ID能力分析.md` |

## 三、本版实现决策

1. **容器框 = Group 节点**。v4.3 数据模型里没有独立的 Container 实体，旧版“容器大框”就是 Group 节点。因此“容器合并”在协议上必然落实为 Group 操作；本版严格按旧版 `combineGroups` 实现，不新增“合并分组”按钮，也不把“槽位放进同一 Group”当作容器合并。
2. **槽位拖动**沿用旧版：只能拖回同一机器框，生成新容器，源容器不能变空；拖动位置写入新容器 `x/y`（相对机器框）。
3. **容器合并**沿用旧版规则与排序；发送前额外校验同机器、类型一致、槽位不重复，并在 UI 显示确认（含源容器管道会被级联删除）。
4. **不实现**机器框合并、外设徽章拆分——旧版存在，但不在 M6 任务范围，避免一次引入过多破坏性操作。
5. 所有拖动结果都通过 `BatchRequest` 走 M5.5.1 写入门禁；失败不改变本地 Factory（无乐观更新）。
6. 旧版没有“合并槽位”功能，本版也不新增。
