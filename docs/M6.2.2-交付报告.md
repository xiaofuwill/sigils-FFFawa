## 3. BatchRequest 执行流程

- **数组结构校验**：`requests` 必须是 table；key 必须是连续正整数 `1..n`；空数组、稀疏数组、字符串 key、小数 key 全部在 mutation 前拒绝。
- **子请求预校验**：每个 child 必须是 table、`type` 为 11 种工厂 mutation 之一、必需字段齐全（PipeAdd 的 pipe.id/from/to、各 Del/Edit 的 ID、GroupAdd 的 group.id/slots 等），可选字段类型也会检查。
- **执行顺序**：校验通过后按 `ipairs` 数组顺序执行，操作 `staged = cloneValue(factory)`。
- **中途失败处理**：立即停止，丢弃 staged，**不提交、不保存**，返回 `ok=false` + message。
- **是否存在回滚**：没有数据库式回滚；因为所有 child 都在 staged 副本上执行，失败时直接丢弃副本，内存 Factory 不变。仍不宣称崩溃安全事务。
- **最终响应语义**：只有全部 child 执行成功且 `saveFactory` 显式返回 `true`，才 `commitFactory` 并发送 `ok=true` + 合并 diff。

失败状态分类：

| 分类 | 行为 |
|---|---|
| `rejected_before_mutation` | 预校验失败，未执行任何 child，无保存 |
| `execution_failed_after_partial_mutation` | staged 已部分修改但被丢弃；内存 Factory 不变；无保存 |
| `save_failed_after_mutation` | staged 被丢弃；`persistenceFailed=true`；返回失败 |
| `saved` | 保存成功 → 提交 staged → 成功响应 |

## 4. 持久化行为

- **saveFactory 返回约定**：成功显式 `return true`；任何失败路径 `error()`。
- **异常处理**：控制器用 `pcall` 捕获，并要求返回值严格等于 `true`；`pcall` 成功但返回非 true 也视为失败。
- **文件打开 / 写入 / 关闭错误处理**：`writeTextFile` 检查 `fs.open`，写入与关闭都包 `pcall`；临时文件写完后做结构校验；失败时删除临时文件并抛错。
- **保存成功后响应证据**：`tests/controllerBatch.test.lua` 用例 1 / 7 断言事件顺序为 `save → send`。
- **保存失败后的控制器状态**：`persistenceFailed = true`；后续 mutation 与 FactoryGet 立即返回 `ok=false`，不再尝试写入，直到重启并通过 `recoverFactory` 恢复。
- **是否仍存在内存 / 磁盘不一致风险**：保存失败时内存 Factory 不变（staged 丢弃），但磁盘可能处于 `.tmp` / `.prev` / `.bak` 的恢复候选状态；启动时 `recoverFactory` 处理。未证明断电级一致性。

时序（成功）：

```text
Editor -> CC: BatchRequest
CC: validate array + all children        (no mutation)
CC: staged = clone(factory)
CC: children in array order on staged
CC: saveFactory(staged)                  -> temp write -> validate -> backup -> prev -> move -> validate
CC: saved == true
CC: commitFactory(factory, staged)
CC -> Editor: ConfirmationResponse ok=true + diff
```

时序（保存失败）：

```text
CC: staged mutated
CC: saveFactory(staged) -> error/false
CC: persistenceFailed = true
CC: drop staged, no commit
CC -> Editor: ConfirmationResponse ok=false + message
CC: subsequent mutation / FactoryGet -> ok=false
```

## 5. Factory writer 审计

| 文件 / 函数 | 修改对象 | 是否 yield | 分类 | 同步方式 |
|---|---|---|---|---|
| `sigils.lua#init` | factory（启动加载 / 外设同步） | 启动阶段 | FACTORY_WRITER | 在所有协程启动前完成 |
| `controller.lua#applySingleRequest/applyBatchRequest/applyPeripheralChange` | staged → factory | save 可能 yield（文件 IO） | FACTORY_WRITER | 单 `os.pullEvent` 循环，事件串行 |
| `factory.lua` mutation helpers | 调用方传入的 staged | 否 | FACTORY_WRITER（被调用） | 仅由 Controller / 启动流程调用 |
| `pipe.lua#processAllPipesForever` | `factory.pipes/groups/missing/slots` 只读；写局部表与缓存 | 是（peripheral、os.sleep、coroutine.yield） | READ_ONLY + TRANSIENT_ONLY | 不写持久化字段，无需 writer gate |
| `pipeBatcher.lua` / `PipeGraph.lua` / `PipeSaturation.lua` | 批次 / 图 / 统计临时表 | 否 | READ_ONLY | — |
| `packageTransport.lua` | 模块级地址/类型缓存 | 是（peripheral 调用） | READ_ONLY + TRANSIENT_ONLY | 缓存按 peripheral generation 失效 |
| `PeripheralCache` / `ItemDetailAndLimitCache` | 运行时缓存 | 是 | TRANSIENT_ONLY | 不进入 factory.json |
| `machine.lua` | 新建机器 / 分组表 | 否 | 构造器 | 不修改现有 Factory |
| `backup-factory.lua` | `factory.json` / `.bak` 文件 | 否 | 文件维护 | 不修改 Factory 表 |

**Pipe.processAllPipesForever 结论：** 逐行审查 + 全项目写入点搜索未发现对 `factory.pipes/groups/machines/missing/available` 的结构性写入；它只读取配置并在 yield 后继续使用旧表引用。`commitFactory` 无 yield，替换顶层 map 内容时不会与 Pipe 协程交错执行；Pipe 可能读到旧配置（陈旧读），但不会写坏 Factory。

**FIFO stale barrier：** 前提仍成立——单编辑器、relay 保序、Controller 单协程串行；Pipe 不是 Factory writer。

## 7. 未解决风险

- **事务回滚**：没有数据库式事务；执行失败靠丢弃 staged 保证内存不变，但磁盘中途状态依赖启动恢复。
- **crash consistency**：未验证断电 / 进程被杀时 `.tmp` / `.prev` / `.bak` 的一致性与 `fs.move` 的真实原子语义。
- **原子文件替换**：CC:T 文件系统没有等价 `rename+fsync` 证明；现有实现用临时文件 + 校验 + `.prev` + 备份，但未做断电测试。
- **后台并发 writer**：当前 Pipe 只读；若未来新增后台 writer，必须纳入同一 mutation gate。
- **Pipe 陈旧引用**：yield 后可能继续使用已替换的 group/pipe 表引用，导致一次基于旧配置的物流操作；不影响 Factory 数据。
- **P06/P07 未模拟**：写入/关闭失败与成功响应发送失败未在运行时覆盖。
- **真实 CC:T / Minecraft / Create 联调**：**未执行**。
